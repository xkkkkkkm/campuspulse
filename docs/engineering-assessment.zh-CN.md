当前技术路线是原生多页面前端 + Spring Boot/Spring MVC + JdbcTemplate + MySQL + Python 离线训练。单体部署对于此规模是合理选择。已有按 auth/activity/team/message 等能力分包，这是有效的第一步。

内部边界尚未清晰：

- 前端 script.js **5,836 行**，CSS **3,784 行**；API、认证状态、DOM 模板、表单、业务逻辑、聊天和管理员逻辑集中，改一处公共逻辑影响很多页面。
- ActivityController **773 行**，TeamController **576 行**，Bootstrap **929 行**。Controller 同时处理权限、业务状态、事务、SQL、通知和响应转换。
- DTO 多以内嵌 record 表达，比完全无结构更好，但数据库结果大量用 Map 和强制转换，缺少独立领域模型、Repository/Service 边界。
- 权限和状态转换分散在多个 Controller，重复逻辑已出现差异；数据表 version 字段没有用于更新条件或递增，不能称为已实现乐观锁。
- 后端镜像复制完整 frontend，Spring 也提供静态资源，同时另有 Node 前端服务；静态服务职责重复，应明确开发模式与部署模式的入口。

建议以功能模块为单位采用 controller → service → repository，业务不变量集中在 service，事务边界覆盖完整用例。前端先拆 API/auth、通用组件、页面入口、消息连接和 i18n 模块。原生 ES modules 就能改善结构；若决定引入 Vue/React + TypeScript，应围绕复用和测试收益选择。

不需要为了架构图引入微服务、服务注册中心、分库分表或 Kubernetes。JdbcTemplate、单体、SSE 本身都不是缺陷。

**6. 数据库与数据层专项**

已有基础包括 InnoDB、主键、关系外键、报名/成员等唯一约束、参数化 SQL、JDBC 生成主键和部分事务。需要补齐：

- **迁移升级**：只有 V1；baseline-on-migrate 对已存在无历史库可跳过 V1，而 CREATE TABLE IF NOT EXISTS 不会补旧表字段。应明确旧库升级路径，提供 V2+ 与新装/升级双重测试。
- **约束与状态**：容量、时间区间、角色与状态值主要靠零散 Java 检查；缺少集中约束、状态转换日志和并发版本管理。
- **查询效率**：活动列表每项查人数和标签，一页 50 项约 102 条 SQL（不含鉴权）。搜索、组队有额外逐项查询；应先批量查询/聚合，再依据 EXPLAIN 与数据量设计复合索引。
- **分页真实性**：部分接口仅 LIMIT 50/100/300，无下一页；全局搜索每类最多选 120 个候选再内存排名，total 只是截断后的数量。
- **历史保留**：手动删除活动/队伍仍为物理删除，并级联清除报名、成员、聊天等。定时任务不再删除活动，不代表删除策略已全面非破坏化。
- **重复数据来源**：schema.sql 与 Flyway、训练脚本内 CREATE TABLE 并存；event_log/user_behavior_log、两套推荐位表需要明确分工，避免不同模块读写不同来源。
- **标签与模型**：团队标签主要从标题/描述推断，缺少明确的 team_tag 关系；模型 score 表以 user/item 为主键，版本被覆盖，active_flag 未形成真正发布控制。
- **存储生命周期**：没有文件归属表、空间配额、孤儿上传清理；验证码、行为、聊天的保留/归档和备份策略不完整。
- **时间处理**：MySQL 配 Asia/Shanghai，后端容器日志为 UTC，业务多用 LocalDateTime/NOW，浏览器再按本地时区解释。跨时区语义需要统一并测试，尤其是英文演示和到期判断。

没有压测或执行计划测量，因此不能声称数据库已能承担某个并发量，也不宜现在就堆缓存替代查询修复。

**7. 安全专项**

已经实现的有效措施：随机盐 PBKDF2、SecureRandom 验证码、验证码哈希存储、SQL 参数绑定、接口鉴权、角色/账号禁用状态回查、上传扩展名与图片内容检查、CORS 来源列表、SSE 短期单次票据、统一隐藏内部错误响应。应保留并用测试证明。

除 F03—F10 外的缺口：

- 接口权限主要手动检查，公开 GET 路径使用较宽前缀规则，新增敏感端点容易漏校验；需要逐接口权限矩阵与越权测试。
- localStorage 存令牌结合已发现的危险 URL 路径构成实际风险；优先修复 XSS，再评估 HttpOnly 会话/令牌方案。若改用 Cookie，需同时设计 CSRF、SameSite 和 CORS。
- 普通用户搜索返回完整学号/用户名；组织者联系方式仅对本人、管理员及已提交或通过报名的用户可见。需要明确可见性设置与最小披露原则，这是隐私策略缺口，不能误称所有信息均匿名公开。
- 上传在限制像素前完整解码；缺少维度/解压内存限制、用户配额、文件引用验证。文件 URL 可直接公开访问，必须明确哪些文件允许公开。
- 匿名客服升级可反复给所有管理员插入通知；启用 Dify 后有资源/费用滥用风险。需要限流、预算/超时边界、工单去重以及独立匿名会话标识。
- 已建立的 SSE 连接没有持续校验禁用/活动资格；活动广播仍能发送消息 ID/时间元数据。消息正文的 HTTP 接口会再次鉴权，不能把它描述为必然泄露完整聊天内容。
- 无完整管理员操作审计、认证审计、密钥轮换、依赖漏洞扫描和安全回归测试。Spring Boot 3.1.4 等依赖版本需评估升级与扫描；本次没有核验具体 CVE，不能据版本直接断言可利用漏洞。
- Compose 默认开发凭据和所有网卡端口绑定只适合受控演示。prod profile 不会自动清除旧卷里的演示账号；切换生产必须使用明确初始化和数据策略。

**8. 并发、异步与实时专项**

现有事务和行锁是部分基础，Java 使用 ConcurrentHashMap 存 SSE 连接/票据只保证这些容器本身线程安全，不等于整个业务并发安全。

需要优先定义的不变量：有限容量不可超员；同一申请不能同时已取消又成为有效成员；同一码只能成功消费一次；重复消息请求不能产生重复消息；业务落库后通知应可追踪成功或失败。

- **幂等**：收藏是 toggle，重试可能逆转操作；消息无 clientMessageId/幂等键；创建和通知缺少一致的去重约定。
- **异步外部调用**：邮件同步发送且未配置完整 SMTP 超时；Dify 已有 5 秒连接/15 秒读取超时，但仍占用请求线程。是否异步取决于体验和吞吐目标；需要有界执行、失败状态和重试，不是简单加 @Async。
- **事件一致性**：多个通知路径 catch 后忽略错误，业务成功但通知丢失不可追踪。可先使用数据库事务内通知记录；跨系统投递再采用 outbox、重试和去重。
- **SSE 压力**：广播在请求/调度路径同步遍历连接，没有每用户连接限制、慢消费者隔离和发送背压。需要限额、有界队列、超时及指标。
- **恢复**：连接心跳已存在，但客户端不监听心跳用于缺口检测；缺少重连票据、补拉和去重闭环。
- **多实例**：ticket 和连接在进程内；没有共享票据与事件总线时，多实例请求可能命中另一进程而失败。Redis/消息代理是横向扩展的条件需求，单实例目标不必强加。
- **定时任务**：已有通知清理任务和心跳，缺少按批清理、失败监控、执行时间记录；多实例重复执行策略未设计。
- **验证**：尚无最后名额竞争、验证码重放、断线恢复、慢连接、故障回滚、数据库暂时不可用等测试。

**9. 推荐、搜索与实验可信度专项**

当前真实实现应描述为：关键词搜索 + 规则推荐 + 基于用户/内容特征的离线梯度提升分类排序，并提供规则回退。

尚未实现或未有效验证：

- LightGBM/LambdaMART、Sentence-BERT、双塔与向量检索仍是规划/可选项；item_embedding 表不等于已接入向量检索。
- SearchController 用 LIKE/contains 加权，返回“关键词与语义匹配”会夸大实际能力。
- 训练把未发生行为的用户×内容组合都作为负样本；与文档中的“曝光后未转化”定义不一致。
- 全量标签先进入历史特征再随机划分，AUC/AP 存在泄漏；需要时间切分、明确曝光窗口、按用户评估和冷启动切片。
- 没有可信的 Recall@K/NDCG@K、规则/热门基线、消融实验、置信区间和规模测试。
- 全量用户×内容特征/相似度/逐条预测写库接近 O(U×I)，小样本能运行不代表能扩展到全校规模。
- 客户端行为入口允许提交 REGISTER/TEAM_JOIN 等转化标签，未验证业务事实，容易污染训练数据；关键转化应由服务端业务事务产生。
- 训练产物和分数版本没有严格原子发布、回滚和过期策略；demo 重启可覆盖分数。即使使用 heuristic fallback，写入原因仍声称“机器学习排序”，需要真实标识来源。
- Python 依赖只有下限，没有锁定环境；CAMPUS_DB_* 与主应用 DB_* 使用不同命名，需要统一说明。
- 训练的 dry-run 仍执行建表逻辑、保存模型文件；MySQL DDL 的隐式提交不能靠 rollback 变成纯只读。应准确命名或真正消除这些写入。

学校审查最值得展示的是明确的实验设计、数据来源、限制和复现命令。算法名称和漂亮指标不能替代这些证据。
